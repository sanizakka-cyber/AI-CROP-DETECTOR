# Staging environment

A copy of MSAS FarmAI for testing, separate from production. It has its own database and its own secrets.

- **Web and API:** `msas-farmai-staging` at https://msas-farmai-staging.onrender.com
- **AI engine:** `msas-ai-engine-staging`, running 3 analyses per scan (`SCAN_PASSES=3`)
- **Database:** `msas-db-staging`
- **Code:** it deploys whatever is on the `staging` git branch.

The Blueprint is `render.staging.yaml`, not `render.yaml`. If production is synced from `render.yaml`, adding staging there would create billable services the moment it merged.

## How staging differs from production

| | Staging | Production |
|---|---|---|
| `APP_ENV` | `staging` | `production` |
| Database | `msas-db-staging`, empty to start | `msas-db` |
| Who can scan | QA accounts only (`QA_SCANS_QA_ONLY=true`), 200 scans a month each | everyone, by plan |
| Payments | Paystack **test** keys only; live keys are switched off outside production | live keys |
| Email | written to the log, never sent | sent |
| Speech ("Listen to your result") | off | not deployed yet |
| CEO account | not created; there is no default password any more | exists |
| Secrets | generated by Render, never in git or logs | set by hand |

## What it costs

- **Web service and AI engine:** free plan. Each sleeps after 15 minutes idle, and the first request afterwards takes about a minute.
- **Database:** Render allows **one free database per workspace**, and a free database expires after 30 days. If production uses the free one, the staging database needs a paid plan, about USD 6–7 a month for the smallest. That is a spending decision for you; nothing is created until you click **Apply**.
- **AI usage:** every staging scan calls Claude 3 times. Use a separate Anthropic API key with its own spending limit (step 4).

## Create it: click by click

1. **Create the `staging` branch.** This is already done for this phase: `staging` points at the Phase 12.2 head. To test another branch later, run `git push origin <branch>:staging --force-with-lease`, which only moves the staging branch.
2. Open https://dashboard.render.com, then **New +** (top right) → **Blueprint**.
3. **Connect a repository** → `sanizakka-cyber/AI-CROP-DETECTOR`. If it is not listed, choose **Configure account** and allow Render to see it.
4. Fill in the form:
   - **Blueprint Name:** `msas-staging`
   - **Branch:** `staging`
   - **Blueprint Path:** `render.staging.yaml`. This is important: the default is `render.yaml`, which is production.
5. Render lists what it will create: `msas-farmai-staging`, `msas-ai-engine-staging` and `msas-db-staging`.
   - Check each plan reads **Free**.
   - If the database shows an error about the free database limit, stop. Either approve a paid database plan, or tell me and I will change the file.
6. Render then asks for the values marked `sync: false`. Paste them; never type them into a chat or a commit:
   - **`ANTHROPIC_API_KEY`:** create a **new** key at console.anthropic.com → API keys, named `msas-staging`, and set a monthly spend limit on it.
   - **`PAYSTACK_PUBLIC_KEY` / `PAYSTACK_SECRET_KEY`:** from the Paystack dashboard with the **Test mode** toggle on (`pk_test_…` / `sk_test_…`). Live keys would be switched off anyway.
7. Click **Apply**. The first build takes about 10 minutes.
8. When both services show **Live**, open https://msas-farmai-staging.onrender.com/api/health. It should answer `ok`.
9. **Check the QA accounts exist:** `msas-farmai-staging` → **Logs**, then search for `QA account ready`. There should be four lines with emails only and no passwords:
   - `qa-farmer@staging.msasagro.com`
   - `qa-dealer@staging.msasagro.com`
   - `qa-extension@staging.msasagro.com`
   - `qa-admin@staging.msasagro.com`
10. **To read a QA password:** `msas-farmai-staging` → **Environment** → `QA_FARMER_PASSWORD` → the eye icon → copy. Keep it in your password manager.

If Render's form has no **Blueprint Path** field, do not apply `render.yaml`. Tell me, and I will give you the manual steps for creating the three services one by one, with the same settings.

## Running the live checks against staging

The scripts read credentials from environment variables, so nobody types a password into a command or a chat. PowerShell:

```powershell
$env:STAGING_URL = "https://msas-farmai-staging.onrender.com"
$env:QA_EMAIL    = "qa-farmer@staging.msasagro.com"
$env:QA_PASSWORD = (Get-Clipboard)     # after copying it from Render (step 10)
py -I scripts\live\parity_check.py --type crop --photo C:\path\to\leaf.jpg --out parity-crop.json
```

`parity_check.py`:
- refuses the production domain;
- scans the photo once the way the app (build 24) sends it and once the way the web page sends it;
- reads both records back the way the app renders them;
- prints OK or DIFF for the outcome, top finding, severity, urgency, "Not certain", "Likely, please confirm" and confidence (within 3 points).

To run the consistency evaluation (`ai-engine/eval/run_eval.py --repeats 5`) against the staging engine, set:
- `ENGINE_URL=https://msas-ai-engine-staging.onrender.com`
- `ENGINE_API_KEY` = the staging engine's `API_KEY` (Render → `msas-ai-engine-staging` → Environment).

## Pointing the Android app at staging

Build 24 talks to production only. To test the app itself against staging, build an APK from the `staging-apk` profile in `mobile/eas.json`, which uses `EXPO_PUBLIC_API_URL=https://msas-farmai-staging.onrender.com/api`. It is a test build: do not publish it.

## Rotating staging secrets

In Render → service → **Environment**, generate a new value (or paste one), then **Save, rebuild and deploy**. The QA seeder runs on every staging deploy, so a new QA password takes effect on the next deploy.
